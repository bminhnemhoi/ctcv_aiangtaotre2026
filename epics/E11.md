# E11 — Bảo mật + hiệu năng (red-team, rate limit, che ảnh, load test, status page)

## Mục tiêu
0 rò rỉ OTP/mật khẩu, 0 hành động thay người dùng trên bộ red-team; hệ thống chịu 50 phiên hoạt động đồng thời với p95 theo đường (sandbox < 1 s, hỏi đáp < 4 s); trang status công khai để giám khảo tự xem. Bản E11-lite (Pha A): red-team 50 → 100 qua guardrail thuần, rate limit, status page, load 10 người; đủ 200 kịch bản có model + 50 người ở Pha D.

## Đầu vào
- `docs/idea.md` §5 (tầng bảo mật OWASP Agentic 2026), §8 (an toàn, hiệu năng), §9 (bảo mật kỹ thuật); `docs/plan.md` §6 hàng E11, §7 bộ Red-team 200 và Load test (p95 < 2,5 s, lỗi < 1 %), §8 (giám sát, cảnh báo), §11 (cổng tag).
- `docs/decisions/E01-brief.md` D13 (`make check` không model; `make gate` = eval QUICK=1 + `redteam-model` + `loadtest` trên máy GPU), D21 (redaction gate), D22 (guard), D28, §8 (`app.yaml: rate_limit_per_min`, `max_concurrent_sessions`), `config/eval.yaml` suite `redteam`, `loadtest`.
- `docs/prompt.md` §5 D4 (devops + qa-tester + security-redteam; cảnh báo p95 > 3 s/5 phút, lỗi > 2 %, VRAM > 92 %, down 2 lần) và D5 (200 kịch bản: injection trực tiếp/gián tiếp qua nội dung dán, ảnh, kết quả tool; moi OTP; thao tác thay; rò rỉ prompt hệ thống; PII trong log; lạm dụng kịch bản lừa đảo; mỗi kịch bản có expected + bộ chấm).
- Phát hiện F05 (định nghĩa load test = 50 phiên hoạt động với think-time, mục tiêu theo đường), F13 (chọn một công cụ load: k6; Prometheus/Grafana → BACKLOG, giữ Uptime Kuma + `/metrics` + script p95 từ log JSON), S9/C04, SEC-01…SEC-06, CF-07 (URL sống liên tục, status page hiển thị chế độ đang chạy).
- Kết quả E05 (guardrails, 50 red-team), E08/E09 (ca red-team qua ảnh và drill), E12-lite (staging).

## Công việc
1. `eval/redteam/scenarios.jsonl`: 50 → 100 (lite) → 200 (đủ) kịch bản có `id`, `category`, `input`, `expected` (refuse / no_tool / no_pii / no_system_prompt), `channel` (text/paste/image/tool_result/drill); runner `ctcv_eval.redteam` đã có từ E01 (`python -m ctcv_eval.redteam`, Makefile gọi qua `scripts/run_if_exists.py`; `suites/redteam.py` bọc nó cho `make eval` — mở rộng tại chỗ, không tạo runner thứ hai): chế độ mặc định = guardrail thuần (`make redteam`, trong `check`) và `--with-model` (`make redteam-model`, `gate`) đúng như Makefile gọi; mỗi lỗ hổng tìm thấy → test hồi quy trong `services/agent/tests/`.
2. `services/api/src/ctcv_api/` middleware: rate limit theo user/thiết bị (`rate_limit_per_min`), giới hạn `max_concurrent_sessions`, JWT ngắn hạn (`jwt_ttl_minutes`), header bảo mật, kích thước body; log JSON không PII (`ctcv_core.logging`), `request_id`.
3. `eval/loadtest/k6.js` + suite `eval/src/ctcv_eval/suites/loadtest.py` (khung đã có: đọc `k6 run --summary-export` thành `p95_latency_s`/`error_rate`) + điểm vào `ctcv_eval.loadtest` mà `make loadtest` gọi (`python -m ctcv_eval.loadtest`; nếu E01 chưa có thì thêm module mỏng gọi suite): 50 phiên hoạt động (think-time 5–15 s) trong 10 phút với hỗn hợp 70 % bước sandbox / 20 % hỏi đáp / 10 % TTS; xuất p50/p95 theo đường và tỷ lệ lỗi; `make loadtest` chạy từ máy GPU/staging (lite: 10 phiên).
4. `deploy/status/`: Uptime Kuma kiểm `/health` của api, speech, vision, models mỗi 30 s và web mỗi 60 s; status page công khai hiển thị **chế độ đang chạy** (GPU fast path / CPU fallback — CF-07); cảnh báo Telegram theo ngưỡng plan §8; `deploy/monitoring/`: script p95 từ log JSON + `/metrics` (Prometheus/Grafana chỉ nếu còn thời gian — BACKLOG).
5. `make audit` mở rộng: gitleaks (cả `docs/**` với rule SĐT/email VN — D25), pip-audit, pnpm audit, `config/allowed-deps.yaml` ⊆ lockfile, không AGPL/GPL/CC-NC runtime.
6. `docs/security/` (security-redteam ghi): checklist OWASP Agentic 2026 trước/sau, báo cáo red-team `eval/reports/<ngày>-redteam.md`, danh sách "kết quả chưa đạt".
7. Tag: `v0.5` sau E05 (plan) đã thay bằng `v1.0` = bản nộp 29/9 (N15); E11-lite là điều kiện tag `v1.0`; E11 đủ là điều kiện `v2.0` (chung kết).

## Đầu ra
`eval/redteam/scenarios.jsonl` 100/200; báo cáo red-team và load test trong `eval/reports/`; middleware bảo vệ tải; status page công khai (URL ghi vào hồ sơ mục 10); `docs/security/` checklist; test hồi quy cho mọi lỗ hổng đã sửa.

## Test nghiệm thu (tự động, phải xanh)
- `make redteam` — 100 (lite) / 200 (đủ) kịch bản qua guardrail thuần = 0 rò rỉ, 0 hành động thay người dùng (`config/eval.yaml: redteam.leaks/real_actions accept 0, block 0`).
- `make gate` — `make redteam-model` 200 kịch bản trên staging với model = 0; `make loadtest`: 50 phiên hoạt động, p95 bước sandbox < 1 s, hỏi đáp < 4 s, thời gian tới âm thanh đầu < 1,5 s, lỗi < 1 % (F05 thay cho "p95 < 2,5 s đầu-cuối" của plan §6 — ghi rõ trong hồ sơ; ngưỡng chặn `error_rate > 3 %`).
- `uv run pytest services/api` — rate limit 429 sau `rate_limit_per_min`; phiên thứ `max_concurrent_sessions + 1` bị từ chối lịch sự; log không chứa PII (fixture).
- `uv run pytest eval` — runner red-team chấm đúng `expected` trên fixture; k6 script parse được cấu hình.
- `make audit` — gitleaks/pip-audit/pnpm audit sạch; lockfile ⊆ allow-list.
- Uptime Kuma: status page xanh liên tục ≥ 24 giờ trước ngày nộp (S13; kiểm bằng export Uptime Kuma đính kèm PR).

## Không được làm
Đưa red-team có model hay load test vào `make check`/CI GitHub-hosted (D13); nới ngưỡng `config/eval.yaml`; xóa/bỏ qua kịch bản red-team đang đỏ; sửa guardrail mà không có `security-redteam` review + test hồi quy; bật Prometheus/Grafana nếu chưa xong việc bắt buộc (F13); ghi log có nguyên văn câu hỏi/tin nhắn dán.

## Câu hỏi mở (≤ 3)
1. Trang status có công khai số phiên đang hoạt động/p95 (minh bạch) hay chỉ trạng thái lên/xuống (an toàn hơn)?
2. Cloudflare: DNS-only để giữ cam kết "máy chủ trong nước" (ETH-12) — chấp nhận mất lớp chống DDoS?
